# 视图复用冻结副本，断点编辑按 Framer 的方式进入第一版

编辑模式中并排显示桌面、平板、手机三个视图，让设计师改一处时立刻看到其他宽度有没有被挤坏，并直接在小屏视图里做断点改动。三个视图复用同一份冻结副本，分别放进不同宽度的 iframe：写在 CSS 里的响应式规则（媒体查询、Tailwind 断点）自动生效，冻结时的页面状态（例如打开的弹窗）保留，视图瞬间出现。代价是靠 JS 判断窗口宽度的响应式不会重新运行，视图上标注"仅反映 CSS 响应式"。

断点编辑沿用 Framer 的模型：桌面视图是主视图，在其中的改动作用于所有断点，除非某个断点已经单独改过该属性；在平板或手机视图中的样式与布局改动只在该断点生效，属性面板标出被单独改过的属性并可重置。结构性改动（换容器、合成或解散 Stack、新建、删除、复制、挪出画布）始终作用于所有视图；某个断点不需要的图层用"在此断点隐藏"表达。改动单记录每条改动的断点（宽度范围），Agent 按项目已有的断点写法落地。

## Considered Options

- **第一版只看不改，断点编辑留到以后**：成本更低，但设计师发现手机版被挤坏后仍要回到对话框描述。为第一版的雄心目标否决。
- **在对应宽度下重新加载页面再冻结**：JS 响应式正确，但冻结时的页面状态丢失、进入编辑模式变慢。已否决。
- **允许按断点做结构性改动**：CSS 无法单独表达，Agent 只能为每个断点写不同的结构，代码会膨胀且容易出错。已否决。

## Consequences

- `done` 核对断点改动时，需要在该断点宽度下的真实页面上读取（例如在对应宽度的隐藏 iframe 中加载同一页面）；读不到时结果为"没能核对"。
- 视图的宽度范围尽量对齐项目已有的断点（例如 Tailwind 的 md、lg），使 Agent 能直接用项目的断点写法落地。
