# 54: 核对描边粗细时先比较样式里写的值

**What to build:** Agent 运行 `done` 时，描边粗细的核对先比较设定它的样式里写的粗细（与面板显示粗细所用的是同一个来源），读不到时才退回 51 的做法，按浏览器画出来的值比较；这样 1x 屏上 1px 与 1.5px 也能分开，不再出现虚假的 ✓。

参考本功能的 spec.md（同目录上一级，"核对"一节），用词以 GLOSSARY.md 为准，并遵守 docs/adr/ 中的决策，尤其是 ADR 0006。

**Blocked by:** 51（已完成）

**Status:** done

- [x] 1x 屏上，设计师把粗细从 1px 改为 1.5px、Agent 没改源码时，`done` 说明页面没有显示；源码改为 1.5px 后，说明页面显示了这条改动
- [x] 源码里写的值与改后值不同时（例如源码写 1.25px、改后值是 1px），`done` 说明页面没有显示
- [x] 粗细经 `var()` 的简写写入时（例如 `border: var(--w) solid`），不把另一条优先级更低、写了 px 的规则当成来源，而是退回按画出来的值比较；面板显示的粗细也随之修正
- [x] 已有属性的核对结果不变

## 背景

- 51 让核对两边都由浏览器画一遍再比较，避免了小数粗细的误报；但 1x 屏上画出来相同的粗细（1px 与 1.5px 都画成 1px）比不出区别：设计师改成 1.5px、Agent 什么都没改，`done` 也会说明页面显示了这条改动，这正是 ADR 0006 要避免的虚假的 ✓。2x 屏上没有这个问题。
- 51 的已知限制里记录了样式来源可能找错：经 `var()` 的简写会让浏览器把各条长写属性读成空，这条规则不参与比较，于是另一条优先级更低的规则可能被当成来源。"Currently set by" 也有同样的问题。

## Comments

**实现记录（2026-10-28）**

- 核对（`check.ts`）：51 的 `AS_DRAWN` 改为 `AS_WRITTEN`，每个属性一个 `draw`（开始观察页面之前把改后值在页面上画一遍，同 51）和一个 `shows`（这个实例是否显示了改后值）。描边的 `shows` 是 `stroke-weight.ts` 新增的 `showsStroke`：逐边比较，这条边在页面上读得到写的值（与面板同一个读法：编辑的内联声明，否则 `sourcesOf` 找到的那条声明里的 px，且这个值画出来与这条边实际画出来的一致）时，拿写的值与改后值直接比较；读不到时，按 51 的做法拿画出来的值比较。颜色、线型照旧比较。所以 1x 屏上源码写 1px、改后值 1.5px 报没有显示；源码写 1.25px、改后值 1.5px 也报没有显示，`actual` 报写的值。
- 读写的值要放一次隐藏元素来校验，所以现在 MutationObserver 回调里也会改动页面。回调里看完后立即 `observer.takeRecords()` 丢掉这些记录，否则回调会被自己触发、无限循环（已用测试确认）。`look` 是同步的，丢掉的只有它自己造成的记录。
- `stroke-weight.ts`：把 51 的 `readWrittenStroke` 拆成 `readSides`（每条边画出来的值与写的值，写的值读不到或校验不过为 null）和 `asWritten`，面板与核对共用。
- 样式来源（`style-source.ts`，面板显示粗细、"Currently set by"、核对共用）：
  - 经 `var()` 的简写：浏览器把 `border: var(--w) solid` 的各条长写属性读成空。现在长写属性读成空时，再看能设定它的边框简写（`border-<边>`、`border-<部分>`、`border`）是否有值，有就把这条简写当作声明，例如 `border: var(--w) solid red`。粗细于是读不出 px，退回画出来的值，不会再把另一条优先级更低、写了 px 的规则当成来源。样式与颜色的长写属性也一样处理。
  - 逻辑属性：Tailwind v4 的 `border-x-*`、`border-y-*`、`border-s-*`、`border-e-*` 写的是 `border-inline-width` 这类逻辑属性。原来的查找只认物理属性，会把 `.border` 的 1px 当成 `border-left-width` 的来源。核对改用写的值以后，`border border-x-[1.5px]` 会被误报为没有显示（Spec 审查发现，51 时按画出来的值比较不受影响）。现在横排时把每条物理边对应的逻辑长写属性（及其简写、经 `var()` 的简写）也算作候选，按级联比较；同一块里两者都写时，后写的为准。竖排不处理。
- `CanvasView.tsx`、`edits.ts` 没有改。
- 测试：
  - 辅接缝 `edits.browser.test.ts`：
    - 核对：1px 与 1.25px 都不是 1.5px（报写的值）。
    - 等热更新期间页面先变成另一个错的值、再变对，结果为显示。
    - 经设计变量写对，结果为显示。
    - 经 `var()` 的简写压过一条写了 px 的规则时，按画出来的值比较。
    - 逻辑属性写的边按写的值比较，同一块里后写的物理边为准。
    - 面板：经 `var()` 的简写压过写了 px 的规则时读画出来的值，来源是那条简写；后写的规则里的逻辑属性读成写的值，从右到左时 inline-start 是右边。
  - 主接缝 `round.spec.ts`：Agent 还没改源码时 `done` 报 "The stroke is 1px solid #E7E5E4, not 1.5px solid #E7E5E4."，改成 3px 仍报没有显示，改成 1.5px 后报显示。

**已知限制**

- 经 `var()` 写的粗细仍按画出来的值比较，1x 屏上画出来相同的粗细比不出区别：源码写 `border: var(--w) solid`、`--w: 1px`，改后值 1.5px，`done` 仍报显示。
- 每次看页面（第一次，以及等热更新期间页面的每次变化）每个实例最多遍历四次样式表，并在页面 `body` 里放一次隐藏元素再取出。页面自己观察 `body` 的 MutationObserver 也会看到这一进一出。
- `sourcesOf` 原有的限制照样影响核对：
  - 容器查询一律当作成立。
  - 跨源的样式表读不到。
  - 内联样式按 `style` 属性的文本重新解析。浏览器序列化时可能把写在逻辑属性之后的物理边并进 `border` 简写，丢掉先后顺序。
  - 找错的来源只有在这块屏幕上画出来不同时才会被校验拦下。
- 逻辑属性只处理横排；竖排的页面仍只认物理属性。`padding-inline` 等其他逻辑属性也不在这张 ticket 里（Tailwind v4 的 `px-*` 写的就是它，"Currently set by" 对它仍找不到来源）。
- 经 `var()` 的边框样式与颜色现在也算来源。Tailwind v4 的 `.border` 写 `border-style: var(--tw-border-style)`，所以描边样式的 "Currently set by" 由原来的预设样式 `*` 变成 `.border`。这更接近实际，但没有 e2e 覆盖。
