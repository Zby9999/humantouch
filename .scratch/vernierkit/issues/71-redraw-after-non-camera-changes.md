# 71: 不动相机的变化之后，改数值仍 ≤ 2 帧

**What to build:** 窗口变高、删掉旁边的视图、视图变矮，这几种变化都不是缩放或平移画布，却会让整排视图进入视野。这类变化之后约 100ms，编辑层像缩放、平移停下后一样，重新只画看得到的部分，改数值保持在 ≤ 2 帧。

参考本功能的 spec.md（同目录上一级），目标与指标以 docs/goals.md 为准，用词以 GLOSSARY.md 为准，并遵守 docs/adr/ 中的决策（ADR 0011）。

**Blocked by:** None (can start immediately)

**Status:** done

- [x] 窗口变高、删掉旁边的视图、视图变矮之后约 100ms，重新只画看得到的部分，和缩放、平移停下后一样。e2e 至少覆盖"删掉旁边的视图"和"窗口变高"两种（反过来的变化也重画，见 Comments）
- [x] 性能测试新加一项：大页面上先做一次上面的变化，再改数值，p95 ≤ 33.3ms（有窗口两次 12.3 / 12.9ms；Layers 面板隐藏着量，原因见 Comments）
- [x] 进入编辑模式、改数值、按住方向键、拖拽这四项照旧达标（有窗口两次都达标）
- [x] 改动前后的数字记在 Comments（docs/goals.md「度量」）

## 背景

- 来自 22 的遗留风险第 4 条。缩小到所有视图都完整可见之后，浏览器会一直把整排视图都画一遍。所以缩放、平移停下约 100ms 后，编辑层让它重新只画看得到的部分。窗口变高这类变化不是缩放、平移，不会触发这一步，要等到下一次缩放、平移停下，或者下一次模式切换的动画结束。在那之前，改数值会回到约 25–34ms，最差超过 33ms 的目标。22 把要不要处理留给主线决定，用户 2026-10-30 决定处理。
- 撤销那一帧的测量拆到了 73（用户 2026-10-30 决定）。
- 有窗口的验收会弹出 Chrome、抢走焦点，跑之前先问设计师；平时用 headless 量。

## Comments

**实现记录（2026-10-31）**

*先查清楚问题出在哪一步*

动手前在 headless 下做了几组探针（没有提交），每组之后在 Gap 上按 8–12 次 ↑，看工作视图那一帧的主线程时间：

- 什么都不做：约 12–14ms。
- 删掉旁边两个视图，把窗口拉高到整排视图都看得到（1440×10200），再拉回 1440×900：约 20ms。这时什么都没重画，整个桌面视图仍被整片画。之后用滚轮平移一下，相机停下后重画了一次，回到约 10ms。
- 只把窗口拉高、不拉回：约 21ms。这时整个视图都在视野里，本来就要整片画，重不重画都一样。
- 在大页面上，删掉旁边两个视图，再删掉页面的主栏（`main`）。桌面视图变矮，整个都看得到。然后 ⌘Z 撤销：Gap 一步 30–36ms。

结论：ticket 22 说的"粘住"，是在整排视图都在视野里时画过一次留下的。

- 窗口变高、删掉旁边的视图、视图变矮，这些变化本身只是让整排视图进入视野。这时整片画是应该的，不算多花。
- 真正变慢，是之后又有一部分离开视野、相机却没动。比如窗口变回去、视图加回来、撤销让视图又变高。这时浏览器仍然整片画，没变慢之前看不出来。
- 所以光在 ticket 列的三种变化之后重画不够，反过来的变化之后也要重画。

另外量了一组：整排视图都在视野里时先重画一次，再把窗口拉回去、不再重画。Gap 一步是 17.0ms，一次都不重画是 21.2ms，两次都重画约 10ms。所以视野里看得全时重画一次也有用，代码里保留，也照 ticket 的写法做了。

*做了什么*

1. **记着"上次重画以后，整排视图有没有全部在视野里过"**。在 `stage-redraw.ts` 的 `onceAtRest` 里。
   - 相机每次移动、每次大小变化时都看一眼。整排视图指所有视图加画布外的图层，在视口里四边都不出界才算看全（`camera.ts` 新加的 `showsWhole`，纯函数）。
   - 每次重画后，按当时是否还看全重新记。
2. **相机没动、大小变了时（新加的 `resized()`）**：如果记着"看全过"，约 100ms 后重新只画看得到的部分。
   - 和相机停下用的是同一个计时（`AT_REST_MS`）。
   - 同样等拖拽、按着、输入文字、模式切换结束后才画。
   - 没看全过就不画。所以大页面上平常改数值、视图跟着变高变矮时，不会每一步之后都多一次约 10ms 的重画。
3. **哪些算大小变化**（`CanvasView.tsx`）：
   - 窗口变大变小（视口的 ResizeObserver）。
   - 视图和画布外图层占的范围变了：删掉或加回视图、视图变高变矮、挪动画布外的图层。
   - 面板开合挪动视口左边时，相机跟着平移，本来就走相机停下那条路，不另算。
   - 视口的大小在 ResizeObserver 里记下，改数值时不用再去量排版。
4. 设计师看到的画面和交互都不变。ADR 0011 讲的是旁边的视图何时跟上，这次没碰；GLOSSARY 没有新词。

*遗留风险*

1. 依赖 Chromium 的内部行为，和 ticket 22 第七、八轮一样。"看全"按视口四边算，假定浏览器只按视口裁剪。Chromium 改了这部分逻辑时，最坏回到改前的数字，不会画错。
2. 整排视图一直看得全时，改数值让视图变高变矮之后约 100ms 会多一次重画（headless 约 10ms 的任务）。正好这时再改数值或开始拖拽，那一帧会慢一些。大页面上平常的缩放看不全，不会这样。
3. 有窗口 Chrome、Layers 隐藏时，新加那项在改前就不慢，没能在有窗口下单独看到画布这部分的改善。Layers 显示时能看到（42 → 34ms）。原因没有查明。
4. 删掉一大块再撤销后，Layers 面板全部展开（约 5250 行），每次改数值多约 20ms，有窗口 Chrome 下 p95 约 37–40ms，超过 2 帧。不是本 ticket 的范围，见下。
