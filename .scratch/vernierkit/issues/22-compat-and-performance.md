*测量方法*

都在大页面上、进入编辑模式后默认的三个视图（桌面、平板 768、手机 390）同时显示、Layers 面板打开时测；时间都在页面里取（`performance.now()`、事件的 `timeStamp`、`requestAnimationFrame`），不靠 Playwright 往返。"一帧画完"的时刻：在那一帧的 `requestAnimationFrame` 回调里用 `scheduler.postTask(…, { priority: "user-blocking" })` 排一个任务，它在这一帧的样式、布局、绘制做完后、在页面已排队的其他任务之前运行。

1. 进入编辑模式：每轮重新加载页面，鼠标先移到切换按钮上停 1 秒（编辑层其余部分在这时加载，ticket 34），点切换按钮；从 click 事件的 `timeStamp` 到"三个视图都显示画布、Layers 面板列出图层"的第一帧画完。之后回到预览模式再进一次，同样计时。先热身一轮不计，再计 8 轮，共 16 个数；达标条件：全部 16 个的中位数 ≤ 150ms。页面缩进画布的 240ms 进场动画是过渡，不计入（它从显示桌面视图的那一帧开始；平板、手机视图在动画结束前隐藏）。另外报告"桌面视图第一帧开始"的时间，供参考。
2. 改数值到画面变化：选中第 6 个商品卡片，在 Design 面板的数值框里按 20 次 ↑，分两种：卡片的 Corner radius（只重绘）和卡片内 Stack 的 Gap（重新排版，卡片、它那一行和下面的内容都动）。卡片在 96 次循环里，改动落到 96 个实例上，三个视图都要变。每次按键记：(a) 按键后画出的第一帧里三个视图是否都已显示新值（在那一帧画完后读计算样式）；(b) 主线程为这次改动花的时间 = 从 keydown 开始处理到处理完（window 上冒泡阶段的监听器）+ 下一帧从 rAF 回调到画完；(c) 从按键事件的 `timeStamp` 到那一帧画完（有屏幕时含等下一次刷新的时间，只作参考）。达标条件：20 次都在第一帧显示，且 (b) 的 95 百分位 ≤ 16.7ms，也就是几乎每一步这一帧都赶得上（留一次给垃圾回收之类）。(a) 在编辑层同步处理按键时几乎总是成立，它防的是改动被推迟到之后的帧；真正卡住的是 (b)。
3. 拖拽：选中第 6 个商品卡片，按住拖 2.5 秒，指针每 8ms 移动一次（经 CDP 直接发给浏览器、不等页面处理完上一次，像真鼠标一样不管页面跟不跟得上；Playwright 自己的 `mouse.move` 每次都等页面处理完，实测每秒只到 23 次，太宽松），在左右各两张卡片之间、上下一行之间来回，期间放置位置不断变化、其他卡片滑开让位；最后按 Esc 放回原处。拖 3 次。用 rAF 记每一帧的时间，算每次拖拽的平均帧率和帧间隔；同时记 long task 和每秒到达页面的 pointermove 数（Chrome 每帧最多交给页面一次，实测约 63 次/秒，也就是几乎每帧都有新的拖动要画）。达标条件：每次拖拽平均 ≥ 58fps，且帧间隔的 95 百分位 ≤ 20.8ms（16.7ms × 1.25，即迟到的帧少于 5%）。显示器是 120Hz 时帧率会更高，条件不变。

*做了的优化*

1. 改数值时就地改编辑样式的规则（`canvas-style.ts`）。原来每改一步都重写该元素的编辑样式 `<style>` 的文字；样式表里有 CSS layer（`@layer vernierkit-edits`），Chromium 对这种样式表的任何文字改动都会把整个文档重新排版、重新绘制，大页面上每个视图要十几毫秒，三个视图加上中间被强制的几次，就是一百多毫秒。现在规则的结构（选择器、断点的 media query）不变、只是声明的值变时，通过 CSSOM 改那几条声明，文字先不写；`data-vk-rules` 里的 JSON 仍是唯一的依据，`syncEditStyles` 在需要文字的地方按它写出：保存画布（`serializeCanvas`）、画布外图层的保存（`serializeEditable`）、新加的视图（`copyCanvas`）、其他视图跟随画布时（`views.ts` 的 follower），以及 `asPage` 读完页面本来的样式后还原。浏览器单测加了 3 条（连续改值后每个视图、保存的画布、之后新加的视图都显示最新值；中途按页面本来的样式读一次不影响；断点与全宽度交替改、撤销回原样）。
2. 冻结和新加视图时先定好 iframe 的宽高再让它算样式（`freezer.ts` 的 `layOut`）。原来先 `getAnimations()`（强制算一次样式）再改 iframe 宽度，宽度一变 media query 跟着变，整页样式又算一遍；现在每个视图少算一次整页样式，大页面上每个视图约 11ms（trace 里看得到少了一次 UpdateLayoutTree），三个视图约 33ms。端到端的中位数只差二十几毫秒，和波动差不多大。

设计师看到的画面、保存的画布和改动单内容都没有变；全量 typecheck、单测 498 条（原 495，加 3）、e2e 270 条通过。

*还差多少、差在哪里（headless trace）*

- 进入编辑模式约 245ms，主要是：冻结时复制 5000 个元素的 JS（约 25ms）和把副本搬进 iframe（约 7ms）；三个视图各自整页算样式（约 12ms）和排版（约 11ms）；两个旁边的视图各自复制节点（各约 9ms）；建图层树（约 31ms）和第一次渲染外壳与 Layers 面板（约 20ms）；最后一帧三个视图第一次绘制（约 17–27ms）；点击后还有一个约 28ms 的帧，trace 里看不到其中做了什么（只有 BeginMainFrame，原因未查明，可能是 headless 软件合成特有的）。光浏览器为三个 5000 元素的文档算样式、排版、绘制就要约 90ms，剩下的 JS 要压到 60ms 以内才有可能达到 150ms，需要动结构（例如图层树按需建、旁边的视图在进场动画期间再排版），不是局部优化能做到的。
- 改 Corner radius 约 43ms：96 个实例各有一个编辑样式表，改 96 个样式表让每个视图的样式失效检查花约 6ms（实验：同样的改动放在一个样式表里约 2.5ms，写在 style 属性上约 1.6ms）；编辑命令本身的 JS 约 12ms；绘制约 8ms。改 Gap 约 73ms：多出来的是排版移动了下面的全部内容，三个视图都要整片重绘（约 33ms）。
- 拖拽约 50fps：平时每帧 14–20ms（绘制约 11ms、Layerize 3–8ms），放置位置一变、旁边的卡片开始滑开时，三个视图各整片重绘一次（一帧 40–60ms，就是那几个 long task）。试过给滑动的卡片加 `will-change`，没有改善，已撤回。

*需要设计决定的问题*

1. "进入编辑模式 ≤ 150ms"的终点：现在按最严的算法，到三个视图和 Layers 面板都出来的那一帧。旁边两个视图在 240ms 的进场动画期间本来就是隐藏的；如果终点定为"桌面视图出现、进场动画开始"，就可以把旁边视图的复制与排版挪到动画期间做，设计师看到的效果不变（动画结束时三个视图都在），但现在两种算法的数字很接近（主线程一直忙到全部做完），只改终点不够，要配合挪工作的顺序。
2. 改数值时 96 个实例各一个样式表：把同一图层的实例并到一条规则（或一个样式表）里能再省每个视图约 4–5ms，但要改编辑样式的数据结构（每个元素一个 key），影响保存的画布格式，需要单开 ticket。
3. 拖拽时整片重绘：可以在拖拽开始时就给同一容器里的兄弟图层设 `translate: 0 0`，让它们一开始就各自成层，之后滑动不再整片重绘；代价是拖拽期间这些兄弟图层各自成为层叠上下文，里面带 z-index 的子元素在拖拽期间的遮挡关系可能变（松手后复原）。这是设计师在拖拽中可能看到的变化，要先确认能不能接受。
4. 达标条件本身：进入编辑模式按 16 次的中位数、并在鼠标先停在切换按钮上 1 秒后点（编辑层其余部分趁这时加载，ticket 34 的设计）；改数值按 95 百分位；拖拽按每次平均 ≥ 58fps 且帧间隔 95 百分位 ≤ 20.8ms。这些是我选的读法，请确认是否要更严（例如进入编辑模式按最差值、或不先悬停）。

读法：

- **按住方向键 Gap**：原来每步之后旁边两个视图跟上的那一帧（约 54ms 的 long task）会和下一步挤在一起，第一下和第一次重复之后的 22 步里，每次有 4–5 步第一帧主线程时间到 55ms 以上（最高约 74ms），p95 约 71ms。现在重复期间旁边的视图不动，这 22 步都在 47ms 以内、多数 31–35ms，p95 降到 37–54ms。剩下拉高 p95 的是第一下和第一次重复（见下）。
- **按住方向键 Corner radius 的中位数反而高了约 5ms**。查了：
  - 录 trace 时两版每一步的组成一样（按键处理约 12ms，下一帧约 14ms，跨度都约 26.5–27ms），桌面视图这一帧的工作没有变多；整段时间里主线程的总工作从每步约 55ms 降到约 30ms（旁边视图每步的样式与绘制没了）。
  - 不录 trace 时差约 5ms；同时让两个 `yes` 进程占着 CPU 再跑，"之后"的 Corner radius 中位数 22.5ms、p95 23.3ms，Gap 30.9 / 33.3ms。
  - 所以这 5ms 来自主线程在两步之间闲下来以后 CPU 降频或换到能效核，不是编辑层多做了事。有窗口的 Chrome 也会这样，验收时要留意。
- **改数值（每步之间停 150ms 以上）**前后差别在波动之内，旁边的视图在两步之间就追上了，第一帧里的工作和原来一样。
- **第一下和第一次重复**：每次按住的第一步约 40–54ms（Radius）/ 74–82ms（Gap），第一次重复约 32–43 / 37–54ms（三次"之后"的运行）。trace 里第一步多了约 17ms 的 microtask 和约 14ms 的样式重算：卡片第一次改这个属性时要新建编辑样式表，这是"其他变化"，旁边的视图当场追上；第二步前后常有一次增量 MajorGC（约 6ms）。24 步的 p95 是第二差的那一步，所以按住方向键的 p95 基本由这两步决定，稳定的步在 28–35ms。
- **有窗口下的预估**：前几轮有窗口比 headless 快约 20%。按此估，按住方向键稳定的步 Radius 约 23ms、Gap 约 27ms，在 33.3ms 以内；p95 受第一下和第一次重复影响，Gap 可能在 33ms 上下。改数值的 p95（Radius 约 27–31ms、Gap 约 37–50ms）中 Gap 仍可能超过 33.3ms。60 预计再省约 5ms。要等 60 做完后用有窗口的 Chrome 验收。

**设计师的回答（第四轮补充，2026-10-30）**

对应"需要设计决定的问题（第四轮）"第 1 条：

- **连续改值**（按住或连按方向键、在数值上拖动等连续输入）：维持现状，旁边的视图停手约 100ms 后一次追上，正在工作的视图下一帧显示每一步。
- **单次改值**（输入数字回车或失焦提交、切换开关、选下拉项、取色、选设计变量等一次性提交）：正在工作的视图下一帧显示；旁边的视图在再下一帧跟上（第三轮的"晚一帧"），不等 100ms。
- 属性面板的输入要告诉编辑器是连续输入还是单次提交；分类覆盖属性面板所有改值入口，有歧义的入口按单次。单次改值紧跟在连续改值之后（旁边的视图还在等停手）时，旁边的视图在下一帧追上到最新值。
- 原有兜底不变：画布上有其他变化、读某个视图、在某个视图里按下时，那个视图立即追上。

**单次改值晚一帧（2026-10-30，headless 参考，非验收）**

*做了什么*

1. **编辑器知道是哪种改值**：`SetOptions` 加 `step`（`edit-commands.ts`）：连续改值中的一步。`editor.set` 收它；`editor.batch` 收它时，批里的每一次 `set` 都算一步。不传就是单次。
2. **旁边的视图按改值的种类跟上**（`views.ts`）：`lagBeside(worked, step)`。
   - 一步：和原来一样，每一步把追上推后，停手 `CATCH_UP_AFTER_MS`（100ms）后一次追上。
   - 单次：画完下一帧后的任务里追上（第三轮的写法，`requestAnimationFrame` 里 `setTimeout`）。还没追上时又来一次单次改值，照样在那一帧后追上。
   - 最新一次改值决定什么时候追上：单次紧跟在一步之后，取消停手的等待，下一帧后追上到最新值；一步紧跟在还没追上的单次之后，改为等停手。
3. **属性面板的分类**（`Properties.tsx`）：连续的入口在交出值时包一层 `asStep`，`update`、`updateEffect` 和 `GridSection` 的 `set` 用 `stepOptions(continues)` 把它传给 `editor.batch`。没包的都是单次，以后新加的入口默认也是单次。

| 入口 | 种类 |
|---|---|
| 数值输入框的 ↑ / ↓（含 ⇧，所有带图标的数值框：X、Y、W/H、Gap、Padding、Opacity、Corner radius 及四角、Font size、Line height、Letter spacing、渐变角度、径向渐变中心与半径、描边粗细及各边、阴影 X/Y/Blur/Spread、Layer blur、Background blur、Grid 的 Columns 与两个 Gap、色标位置） | 连续 |
| 在数值图标上拖动（同上各数值框的图标） | 连续 |
| 拖动渐变条上的色标、色标上按方向键 | 连续 |
| 在输入框里输入后回车或离开输入框（数值、最小最大宽高、十六进制颜色、颜色不透明度、色标位置） | 单次 |
| 开关（Visible、Clip content、Wrap 等勾选框） | 单次 |
| 下拉项（尺寸方式、填充类型、描边线型与描在哪些边、效果类型、字体、字重等 `<select>`，文字对齐、大小写、装饰等按钮组） | 单次 |
| 方向、对齐等按钮 | 单次 |
| 取色（系统取色器 `<input type="color">`，以及颜色选择弹层里的自定义颜色） | 单次 |
| 选设计变量、解除绑定、在输入框里输入后从提示里选变量 | 单次 |
| 添加或删除填充、描边、阴影、色标，点渐变条添加色标 | 单次 |
| 断点标记的"恢复为继承"（`BreakpointMark`、`BreakpointSection`） | 不经过 `editor.set`，算"画布上有其他变化"，三个视图立即追上（和原来一样） |

   取色归为单次是按设计师的列表：系统取色器打开后拖动时，浏览器会连续发 `input`，每一次都按单次处理（旁边的视图每次晚一帧），和第三轮一样；撤销仍按原来的 `continues` 合成一步。

4. **测试**：
   - 单测（`edits.browser.test.ts`，510 → 512）：单次改值后旁边的视图在下一帧画完后的任务里显示新值，之前不显示；连续几步之后紧跟单次改值，旁边的视图在那一帧后追上到最新值，不等停手（用假的 `setTimeout`，把实现改成"单次不取消停手的等待"时这条会失败）。原来"在桌面视图改值"那条的各步加上 `step: true`，行为不变。
   - e2e（`views.spec.ts`，271 → 272）：在页面里逐帧看平板视图，回车提交和点开关后，从按键/点击算起不超过 3 帧平板视图显示新值；按 ↑ 和在图标上拖动时，从最后一次按键/移动算起至少 100ms 才显示。把 ↑ 改成不包 `asStep` 时这条会失败。`promote.spec.ts` 的一处注释改为"输入的值下一帧后显示"。

读法：

- **进入编辑模式**：两次都达标（139.8、134.2ms），比上一次有窗口的 118.8ms 慢了 15–20ms。首次进入的中位数两次都略过 150ms（153.3、155.5ms），16 次合起来仍在 150ms 以内，余量约 10–16ms。这项验收项本来就是勾上的，保持。没过 150ms 时才做的"建图层树挪到进场动画期间"（设计师已预先同意），这次不需要，也没做。
- **改数值（Gap）**：
  - 第一次 p95 34.6ms，超了 1.3ms；第二次 31.7ms，达标。
  - Corner radius 两次都很宽裕（p95 约 20ms），ticket 60 之后比上一次有窗口的 22.7ms 又低了约 2–3ms。
  - Gap 的中位数两次差了 5ms（32.3 / 27.0ms），p95 落在 33.3ms 上下，取决于当时机器的状态。
- **按住方向键（Gap）**：
  - p95 是 24 步里第二差的那一步。两次都是第一次重复（第 2 步）：第一次 37.7ms，超了 4.4ms；第二次 32.1ms，达标。
  - 最差的都是第一下（60.3 / 50.7ms）。卡片第一次改这个属性时要新建编辑样式，算"其他变化"，旁边的视图当场追上，见第四轮的读法。
  - 其余 22 步两次都在 20–29ms。
  - 所以这一项基本由第一下和第一次重复决定。
- **拖拽**：
  - 第二次帧间隔 p95 正好 25.0ms（3 次 120Hz 刷新），超了 4.2ms；第一次 17.6ms，达标。
  - 迟到的帧（超过 25ms）两次都在 5% 以内（3.9%、4.5%），平均帧率每次都在 70fps 左右，0 个 long task。
  - 第二次 p95 没过，是因为间隔正好 25ms 的帧（只晚一次 120Hz 刷新）在 5% 上下，算不进"迟到"，却进了 p95。这次屏幕主要按 60Hz 节奏、可变刷新出帧；上一次按 120Hz 出帧，p95 是 17.6ms。
- **按"两次都达标才勾"**：
  - 进入编辑模式：两次都达标，保持勾上。
  - 改数值到画面变化 ≤ 2 帧：第一次 Gap 的改数值与按住方向键都没过，不勾。
  - 拖拽保持 60fps：第二次帧间隔 p95 没过。它在第三轮后按一次有窗口的结果勾上了，这次按两次都要达标的读法改回未勾。
- 状态保持 ready-for-agent。

*没过的项、差多少*

1. **改数值（Gap）**：改数值的 p95 第一次 34.6ms，比 33.3ms 多 1.3ms；按住方向键的 p95 第一次 37.7ms，多 4.4ms。第二次两项都达标（31.7、32.1ms）。Corner radius 两次都达标。
2. **拖拽**：帧间隔 p95 第二次 25.0ms，比 20.8ms 多 4.2ms。第一次 17.6ms 达标。平均帧率与迟到帧两次都达标。

两项都是一次过、一次不过，差得不多，落在这台电脑两次运行之间的波动里。要两次都稳定达标，Gap 需要再省约 5ms（主要是第一下和第一次重复），拖拽要减少间隔 25ms 的帧。之后做哪项优化，由主线决定。
