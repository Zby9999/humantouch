# 153: 拖角改尺寸在有窗口的 Chrome 里掉到 60fps 以下

**What to build:** 规划会话 2026-11-11 晚在 main 7969441 上跑有窗口的 perf（设计师离开电脑，可以开窗口），发现一条没达标：

- `e2e/perf/flex.perf.ts:1255` 「dragging a layer's handle keeps 60fps」：拖一张卡片的角改尺寸，所有实例跟着变，5006 个元素，3 个视图。
- 本次 57.2fps。机器上同时还有两个验证在跑时，单独重跑 3 次都在 51–52fps。目标是每次 ≥ 58fps，帧间隔 p95 ≤ 20.8ms。
- headless perf 20/20 都过，因为 headless 量不到真的帧。

**不是 134、140 带来的，是从 11-05 起一直在掉。** 同一台机器上，以前有窗口跑的记录（`e2e/perf/results/*-chrome.json` 里的 `resize`）：

| 时间 | fps 中位数 | 帧间隔中位数 / p95 |
|---|---|---|
| 11-05 09:56 | 83.8 | 8.5 / 17.1ms |
| 11-10 09:44 | 70.3 | 16.6 / 17.7ms |
| 11-10 12:42 | 68.3 | 16.6 / 24.8ms |
| 11-10 13:40 | 60.2 和 53.5（两次） | 16.7 / 24.9ms |
| 11-10 18:55 | 49.1（已不达标，当时没人报） | 24.1 / 33.4ms |
| 11-11 21:10 | 57.2；重跑 51–52 | 16.7 / 25.2ms |

同一次里，拖动图层（不改尺寸）一直是 120fps，所以屏幕和窗口没问题，变慢的是改尺寸每一帧要做的事。

要做到：

- 找出是哪几次合并让改尺寸的每一帧变重。比如在 11-05 到 11-10 晚上的 main 合并之间二分，每个点只跑这一条，有窗口，`--repeat-each=3`。还要确认测试本身有没有变重，比如视图从 1 个变成 3 个、实例变多。
- 修到这条测试有窗口时稳定达标，在机器空闲时测。不靠放宽目标。
- 如果某个变重是功能要的，比如 3 个视图都要实时跟着变，就在 Comments 写清楚每一帧的钱花在哪、修法的取舍。

参考 docs/goals.md 的 60fps 目标、ticket 105（有窗口的 perf 余量薄）；用词以 GLOSSARY.md 为准。
