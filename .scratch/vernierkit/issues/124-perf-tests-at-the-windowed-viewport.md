# 124: 119 和 121 加的两个 perf 测试，在加窗 Chrome 那么高的视口里过不了

**What to build:** perf 测试的验收数字在加窗 Chrome 里取。窗口是 1440×900，去掉 Chrome 自己的标签栏和地址栏，页面视口约 1440×813；11-10 那次加窗运行的日志写着 "in a viewport 813px tall"。headless 则直接用 1440×900 的视口。

119 和 121 加的这两个测试，之前只在 headless 里跑过：

- **119 的「选中 96 张卡片之一，下一帧出现在 Design 面板」**：加窗时 20 次里只有 18 次在第一帧出现。没过的是最后两次（第 28、29 张卡片），它们的 work 只有 1.3ms 和 1.4ms，像是 Escape 什么也没选中。headless 只报数，不检查目标，所以之前没人看到。
- **121 的「20 条注释时，拖拽和缩放保持 60fps」**：问题出在写注释的准备步骤。用 Brief 工具 ⌘ 加点击之后，一直等不到 Brief 输入框，8.8 秒就失败了。

两项都稳定复现：加窗单独重跑一样失败。headless 用 1440×900 能过；把视口设成 1440×813，两项照样复现。所以原因在视口的高度。

规划会话推测是测试点到了视口外，或者点在浮在画布上的东西（工具栏、注释卡片）下面，但没有证实。

要做到：
- 先确认原因。是测试的问题，就修测试。如果是产品在矮一些的视口里的问题，比如用 Brief 工具要点的地方被挡住、设计师也点不到，就写进 Comments，并告诉规划会话，不要自己改产品。
- headless 的视口改成和加窗 Chrome 的页面视口一样高，这类问题以后在 headless 里就能先发现。这会改变 headless 的参考数字，在 Comments 里写明前后的差别。

### 实现记录（2026-11-10；起点 main e36a1c8，分支 worktree-agent-a34cac11dd3722f08）

**原因：两项都是测试的问题，不是产品的问题。** 在 headless 1440×813 下两项都复现了。我在点击处记下了 `elementFromPoint` 拿到的元素：

- **119 选中卡片**：测试拿 `cardBody(10..29)` 的 boundingBox 直接去点，从来不平移画布。视口 813 高时，第 21–29 张卡片的点击点在 y = 888、995、1102，全在视口下面，设计师点不到。Playwright 照样把点击发出去，Chrome 对视口外的点击有时能命中、有时不能。第 28、29 张（y 995 / 1102）没选中，Escape 就什么也没选，所以 work 只有 1.3ms。视口 900 高时，995 和 1102 也在视口外，只是碰巧都命中了。
- **121 写 20 条注释**：测试挑的下一个点（x≈700，y≈9）在视口上边附近（审查后更正，见下面「审查后的修正」：不是页面顶部离视口上边只有 8px），正好落在 **Selection 工具栏的 Promote 按钮**上（`AboveCanvas.tsx` 里的 `.tk-selection-tool`）。上一个写了注释的图层有改动可以推，这个按钮就出现在它的右上角。⌘ 加点击点在按钮上不会选中图层，所以 Brief 输入框一直不出现。工具栏本来就设计成浮在图层旁边；设计师看得见按钮，会点旁边，或者先平移一下，所以这不是产品问题。

**没有发现产品问题。**

**改了什么**（只改了 `e2e/perf/`）
- `playwright.config.ts`：headless 的视口改成 `HEADLESS_VIEWPORT = { width: 1440, height: 813 }`，注释写明这是 2026-11-10 在设计师电脑上量到的加窗 Chrome 页面视口。加窗那边不变：`viewport: null`，`--window-size` 仍用 `WINDOW` 1440×900。
- `flex.perf.ts`：
  - 新加 `coveringAt(page, at)`。如果某个点不能当作画布点，它说出原因：在视口外、在编辑器面板上，或者落在画布上浮着的按钮、输入框、工具栏、注释卡片、视图标题上。能点到画布时返回 undefined。
  - `selectDeepestIn` 在点之前先 `expect(coveringAt(...)).toBeUndefined()`。以后再点到视口外或按钮下面，测试会直接报出点到了什么，不会悄悄测成别的东西。
  - 新加 `bringCardIntoSight(page, n)`：像设计师那样用滚轮平移画布，直到卡片的点击点离视口每条边都超过 40px、上面也没有东西挡着为止，最多平移 5 次。119 那项每选一张卡片之前先调用它。
  - `withBriefs` 挑点时跳过被 `coveringAt` 判为挡住的点，并记进 `tried`。

### 审查后的修正（2026-11-10）

以下以本节为准。上面「原因」里 121 那条，以及「改了什么」里的说法，凡与本节不同的都按本节。

**121 的原因说错了，结论和修法不变。** 上面原来写「`Shift+1` 后页面顶部离视口上边只有约 8px」，这不对：`fitCamera`（`camera.ts`）总会在上面留出 `TOP = 72`px。我在 813 下加了临时日志重跑，看到的是：
- `Shift+1` 之后、`withBriefs` 还没滚动的时候，Canvas iframe 的框是 x 692、y −264、宽 28.8、高 582，缩放 0.02。
- 缩放停在 `MIN_ZOOM`（2%），说明适配用的范围在 2% 时仍比视口高。最可能是手机视图（窄，所以页面最长）。按 `fitCamera` 的式子反推，范围约 68000px 高；这个数是推出来的，没有直接量。
- 所以视图垂直居中后，顶部在窗口上方，桌面视图的顶在 y≈−264。按同一个式子，900 高时约在 −220，也在窗口外。
- 测试挑到的 y≈8–10 的点，是被视口上边截住的元素的顶部，不是页面的顶部。点 x≈700 时，上一个写了注释的图层的 Promote 按钮正好在那里。

这是大页面在最小缩放下的正常表现，`fitCamera` 留的 72px 没有问题。要不要让 `Shift+1` 在 2% 时也装下所有视图，是另一个问题，本票不管，产品不动。

**改了什么**
- `withBriefs` 里那行代码注释改了，不再说「页面顶部在工具栏下面」。
- 被挡住的点不再记进 `tried`。Promote 工具栏和注释卡片会随选中和画布移动，所以这个点这一轮跳过，下一轮重新看；没有别的点可挑时，照原来的做法平移（最多 20 次）。
- `withBriefs` 自己的 ⌘ 点击之前也调用 `expectCanvasAt`。以后界面变了，点被挡住时会马上失败，并报出挡住它的是什么（"…, nothing covering it"），不会再等 8.8 秒 Brief 输入框。
- 去掉重复：
  - 新加 `inViewport(viewport, at, margin)`，边距用两个有名字、有注释的常量：`EDGE_MARGIN = 8`（挑点）和 `SIGHT_MARGIN = 40`（`bringCardIntoSight`）。
  - 新加 `justInside(box)`（框左上角往里 3px），`selectDeepestIn` 和 `bringCardIntoSight` 共用。
  - `expectCanvasAt` 由 `selectDeepestIn` 和 `withBriefs` 共用。
- `coveringAt` 的提示把浏览器窗口叫 "window"（"out of the 1440×813 window"），"viewport" 只指 Canvas viewport。

**验证**：`pnpm typecheck` 过；`TK_PERF_HEADLESS=1 TK_PERF_PORT=6110 pnpm test:perf`（813）20 过，没有断言失败。选中卡片 20/20 在第一帧出现；20 条注释那项拖拽、缩放的 fps 中位数都是 60.0。日志是实现子 agent scratchpad 里的 `perf-813c.log`。
