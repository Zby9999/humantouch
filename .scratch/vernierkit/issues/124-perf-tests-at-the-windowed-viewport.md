# 124: 119 和 121 加的两个 perf 测试，在加窗 Chrome 那么高的视口里过不了

**What to build:** perf 测试的验收数字在加窗 Chrome 里取。窗口是 1440×900，去掉 Chrome 自己的标签栏和地址栏，页面视口约 1440×813；11-10 那次加窗运行的日志写着 "in a viewport 813px tall"。headless 则直接用 1440×900 的视口。

119 和 121 加的这两个测试，之前只在 headless 里跑过：

- **119 的「选中 96 张卡片之一，下一帧出现在 Design 面板」**：加窗时 20 次里只有 18 次在第一帧出现。没过的是最后两次（第 28、29 张卡片），它们的 work 只有 1.3ms 和 1.4ms，像是 Escape 什么也没选中。headless 只报数，不检查目标，所以之前没人看到。
- **121 的「20 条注释时，拖拽和缩放保持 60fps」**：问题出在写注释的准备步骤。用 Brief 工具 ⌘ 加点击之后，一直等不到 Brief 输入框，8.8 秒就失败了。

两项都稳定复现：加窗单独重跑一样失败。headless 用 1440×900 能过；把视口设成 1440×813，两项照样复现。所以原因在视口的高度。

规划会话推测是测试点到了视口外，或者点在浮在画布上的东西（工具栏、注释卡片）下面，但没有证实。

要做到：
- 先确认原因。是测试的问题，就修测试。如果是产品在矮一些的视口里的问题，比如用 Brief 工具要点的地方被挡住、设计师也点不到，就写进 Comments，并告诉规划会话，不要自己改产品。
- headless 的视口改成和加窗 Chrome 的页面视口一样高，这类问题以后在 headless 里就能先发现。这会改变 headless 的参考数字，在 Comments 里写明前后的差别。
