**补修：页面怎么核对、断点逐段、`finish` 排好报告（2026-10-31，提交 aa899bd、4ff531e、aba6682 和本条，起点 751c288）**

起因：65 之后 Claude 每项都达标，Cursor 整轮用时比基线 B 高 39%。慢运行分析（只读 transcript）显示多出来的时间几乎都是模型在想、在绕路，起因是说明有缺口：原 Skill 讲页面怎么核对的那段删了，命令输出里没补，Cursor 去读 `node_modules/vernierkit`；phone-breakpoints 写「从 1 到 2」，页面在 640–767px 却是 3 列；「Breakpoints」的例子被套到 768px；Cursor 自己起 vite、开浏览器。总调度定了下面七项，这次只复测 Claude。

做了什么：

1. **说清页面怎么核对。**
   - 「How to write them」最后加一条「How the page checks」，只写这一轮出现的种类，每种一次：
     - 样式改动读浏览器对参考样式里那几个 CSS 属性算出的值（`getComputedStyle`），每个实例都看；
     - 所有断点的改动在页面宽度和每个视图宽度看；
     - 断点改动在项目断点切出的每一段各看一个宽度；
     - 自由定位看画出来的位置，重排看顺序，删除看图层不在了；
     - 页面核对不了的种类点名列出（`done` 会说没能核对，不是错误）。
     - 末尾一句：没显示时 `done` 会给出页面上的值和宽度，不必再去找它怎么核对。
     - 哪些种类能核对，照 `check.ts` 的规则判断（review 后对齐：换容器、裹了 `<span>` 的移动、从自由定位挪回流式的移动都算核对不了）。
   - 原来「All breakpoints」里那句 `done` 怎么核对挪到这一条，不再说两遍。
   - `done` 说没显示时，样式改动多说读的是哪个 CSS 属性（「as the browser computes `grid-template-columns` on the layer」）；断点改动也给出宽度，并说改动在那个宽度也生效。原来断点改动没显示时不说宽度，只说「Something overrides your change」。
2. **断点改动逐段写改前 → 改后。**
   - 断点范围里有项目断点时（手机视图的 0–767px 里有 Tailwind 的 `sm` 640px），编辑层把范围切成几段（`partsOf`）。
   - 设计师改完约半秒，编辑层在页面的一份副本上每段取一个宽度，读出页面现在（代码还没改）的值，记进改动（`parts`）再保存一次（`range-parts.ts`，从 `Shell.tsx` 调）。
   - 各段的值不同时，设计意图逐段写：「below 640px (`max-sm:`), from 1 to 2; 640px to 767px (`sm:max-md:`), from 3 to 2」，断点一行不再写「改前的值是它在这些宽度显示的值」。各段相同时照旧只写一次。
   - 页面核对也按段：每段看一个宽度（窗口所在的那段在窗口宽度，其余在下沿，从 0 起的在上沿减 1px）。原来只看 767px：Agent 只改了 `sm:max-md:` 时，390px 还是 1 列，也算显示了。
   - 读不到时照旧：设计师半秒内就离开编辑模式或 Agent 已认领、之前保存的一轮（打开时原样，不补读）。
3. **说明页面和开发服务器已经开着。** `claim` 开头一句：「The designer's page and its dev server are running already, and the page checks your edits as the code changes: start no dev server, and open no browser to look.」review 后改为有打开的页面时才说（`checks.json` 里有页面、本机服务还在）。
4. **「Breakpoints」不再举具体类名。** 改成：照断点一行的写法；设计意图逐段给出时每段各有设值的类或规则，都改到新值；正好覆盖那段宽度（或一段）的类就改它，不另加。「Absolute at a breakpoint」里的 `max-md:` 例子也去掉了。「All breakpoints」的 `grid-cols-1 sm:grid-cols-3` → `grid-cols-2` 留着：它说的是所有宽度，没有套错范围的问题。
5. **`finish` 先排好报告（ADR 0013）。**
   - `finish` 末尾给出这一轮的报告骨架，按页面核对的结果分好：
     - 已落地的放 ✓；
     - 页面没显示的放 ⚠️，Why 先填好页面上的值和宽度，后面留 `<what keeps it so>`；
     - 没 `done` 的放 ⚠️，Why 留给 Agent；
     - 页面看不出来、`done` 过的先放 ✓，下面一句「看不出来的这几条，照做了就留在 ✓，没有就挪到 ⚠️ 并写两行」。

**补修二：按段读值分片做，离开编辑模式或马上认领也读得到（2026-10-31，起点 7ce0b99）**

起因：上一条补修留下两处风险（见上面「没改的」第 2、3 条）。

- 按段读值时，整份复制页面、读值都在同一个任务里做完。约 5000 个元素的页面上，设计师每做一条断点上的样式改动，就会出现一次 long task。
- 设计师一秒内离开编辑模式，或 Agent 马上认领，各段就读不到，之后也不补读。这时说明退回只写一个值，核对退回只看一个宽度。正是这种旧说明让 Cursor 去读了包里的源码。

修法：

1. **一步一个任务。**
   - 每段的读值拆成四步：建副本、同步、排版、读值（`range-parts.ts` 的 `measureParts`）。每步各占一个任务，沿用 64 里核对准备副本的做法；各段、各条改动依次读，同一时间只有一份副本。
   - 两步之间用 `MessageChannel` 让出，不用计时器：后台标签页里计时器要等一秒以上，而 `claim` 在等这次读值。
   - 每一步都记一个 `vernierkit:parts` 的 performance measure，供性能测试归因。
2. **先标「待读」，谁都能读完。**
   - 改动记下时，范围被项目断点切成几段的，在改动单里标为待读（`parts: null`），随这一轮保存（`Shell.tsx`）。
   - 读值的是编辑层本身（`EditorLayer.tsx`），不再是编辑模式的界面：
     - 保存的这一轮里有待读的改动、又没有认领，它就读；
     - 读完马上再保存一次；
     - 编辑模式开着时，经 `RoundControl.partsRead` 记进画布上的改动单再保存；
     - 编辑模式已经关了，直接写进保存的这一轮（`saved-round.ts` 的 `withPartsRead`）。
   - 所以设计师马上离开编辑模式、保存这一轮之后，或重新打开页面后，待读的都会读完。
   - 页面要先等本机服务说了这一轮的状态才读：认领之后不读，代码已经归 Agent 改了。
3. **`claim` 先等再认领。**
   - 这一轮还没认领、改动单里有待读的改动、`checks.json` 说有打开的页面且本机服务还在时，`claim` 先等页面读完、再保存（最多 5 秒），然后才写认领状态、打印说明（`cli.ts` 的 `waitForPartsRead`）。
   - 没有打开的页面，或 5 秒内没读完：照旧只写视图里的值，`null` 不会出现在说明里（`check.ts`、`change-notes.ts` 都把它当作没有分段）。
4. **review 时一起修的：**
   - 在更窄的断点上改同一属性时，原来的改动被切成几块，每块原样带走了整段范围的 `parts`。现在每块都不带，各自按自己的范围重新读（`edits.ts` 的 `cutting`）。
   - 编辑模式关着时写进分段，改动列表里的撤销记录不再因此作废。

2. 「Breakpoints」在「A class that holds at exactly the widths … beside it.」后加一句：「With Tailwind, of the classes for a property that hold at a width, the one latest in the stylesheet shows, whatever their order in `class`: those with no breakpoint variant come first, then the `max-*` ones from the widest, then `sm:`, `md:` and on up, each directly followed by the ranges that start there (`sm:max-lg:`).」
   - 怎么核对的：在 scratchpad 里分别用示例项目自己的 Tailwind 编译出 CSS，看规则的先后，没有改示例项目。

     - 然后是 `md:`，紧跟着 `md:max-lg:`；再往上是 `lg:`。

**button-over-rule 为什么从 64 起变慢（只读对话记录，没改）**

读的是 B' 3 次（`bench-results/agents/2026-10-31T08-31-09-baselineBprime-067d737/`；B' 的第二个文件夹里没有这个场景）、9623bd4 3 次、e5b2877 3 次。

- Agent 读到的改动部分逐字相同：B' 的 `claim` 输出里两节（Fill、Corner radius）和现在一字不差，Scope 都是「Change it where it is written, at Location」，Variables 都给了 `bg-[#2563EB]`、`rounded-lg`。
- 不同在两处：
  - 写法在哪、旁边是什么。B' 先读 24,653 字的 Skill，两句写法在第 76–77 行，夹在约 20 条里，第 90 行还有「Change exactly the scope given, no more and no less」。现在是 `claim` 末尾 5 条里的两条，紧挨着改动。两边的说法几乎一样：B'「change that rule, narrow it, or use the class's important form (`bg-blue-600!`) as a last resort」；现在「Change that rule, narrow it, or, as a last resort, use the class's important form (`bg-blue-600!`)」。
  - 现在多了「How the page checks」：「the page reads a style change by the value the browser computes … whatever class or rule gives it」。B' 的 Skill 里没有这句。
- 最后写的代码不一样：
  - B' 3 次都在按钮上加 `rounded-lg! bg-[#2563EB]!`，没动 CSS。
  - 9623bd4：1 次把 `button` 规则挪进 `@layer base`，1 次改成 `[role="dialog"] button`，1 次 `:not([data-testid="hero"]) > button`，都在按钮上加普通类。
  - e5b2877：2 次 `button:not(section[data-testid="hero"] > button)`，1 次 `button:not(.rounded-lg)`，都在按钮上加普通类。
  - 9 次都 1:1。
- 时间都花在同一个来回上：认领后最长一段思考 B' 17、28、20 秒，9623bd4 48、42、41 秒，e5b2877 72、66（后面又有 36、37、39）、55 秒。
- 原话：
  - B' #3 选了 `!`：「若要通过 `button:not(.xxx)` 缩小规则范围，必须为其添加新类并修改共享 CSS 规则，这与不改动全局样式的目标相冲突」；B' #2：「通过修改选择器来排除该按钮的做法过于脆弱」。
  - 现在把「last resort」当成先后：e5b2877 #1「按优先级，首选修改或收窄该规则；仅在最后手段时才使用 `!` 强制覆盖」，#3「收窄选择器比 `!important` 更优先」，9623bd4 #2「技能将 `!important` 视为最后手段，因此仍坚持收紧选择器的方案」。
  - 读到核对方式后又多出一条路：e5b2877 #1「页面检测的是 App 按钮层的计算样式。若修改全局 `button` 规则，App 按钮同样会显示变更，这反而能通过检测」，#2「页面检查只看计算样式，因此两种方式都能通过」。
  - 9 次里提到「最后手段 / last resort」的次数：B' 0、1、2；9623bd4 2、3、2；e5b2877 5、6、0。提到「计算样式」：B' 0、0、0；之后 6 次里 4 次有。
- 结论：查不出一句说不清的话。同一句「last resort」，在 Skill 里被大量别的写法冲淡，Cursor 选了 `!`；在 `claim` 末尾紧挨着改动，就被当成要先试收窄。加上核对只看计算样式，它还会权衡要不要干脆改全局规则。要缩短这段思考，就得在写法之间选一种，改的是 Agent 写出的代码。按交代，这是设计问题，没改。
- 可选的写法和后果（都要两家复测）：
  1. **用 `!`**：规则还管着范围外的元素时，在这个图层上用类的 important 形式（`bg-[#2563EB]!`），不动那条规则。B' 就是这样写的，最快。代价：`!important` 留在代码里；同一属性以后再改，也只能继续用 `!`。
  2. **收窄规则**：把规则改成不管这个图层，再在图层上写普通类。现在 6 次都这样写。代价：Agent 得自己找选择器的钩子，写出来的 `:not(.rounded-lg)`、`section[data-testid="hero"] > button` 都靠类名或测试属性，不稳；还要动全局 CSS。
  3. **把规则挪进 `@layer base`**：工具类从此都能盖过它，是 Tailwind v4 本来的写法。代价：影响整个项目，所有元素上和这条规则冲突的类都会突然生效；这个场景里对话框按钮没有这类类，看不出差别，别的项目可能有。
  4. **不改**：三种都可以，1:1 一直 100%，代价是这个场景每次多 30–60 秒思考。
  - 不管选哪种，「How the page checks」那句「whatever class or rule gives it」可以考虑只在样式改动之外说，或者不提「rule」，免得 Agent 想到改全局规则也能通过。这也要和上面的选择一起定。

**补修五（11/01，设计师定的写法）**

起因：补修四查明的 button-over-rule 变慢。`claim` 末尾那句「Change that rule, narrow it, or, as a last resort, use the class's important form」被 Cursor 当成先后顺序，6/6 次先去收窄全局 `button` 规则，最长一段思考 41–72 秒；「How the page checks」里的「whatever class or rule gives it」又让它想到改全局规则也能过核对。设计师 2026-11-01 在补修四列的四种写法里定了第 1 种（用 `!`），并要「How the page checks」补一句。

改了什么（`writing-rules.ts`，只改三句的字，没改什么时候打印）：

1. 「What sets the value now」：规则管的元素都在范围内时才改规则本身；还管着范围外的元素时不动它，只为这个图层覆盖，Tailwind 在图层上写类，CSS 文件、CSS Modules 为图层自己的类写一条规则（不引入 `!`）。
   - 改前：「start from what **Currently set by** names, and change that: a class, replace it; a rule, change it, or, when the rule styles elements outside the scope too, override it for this layer only.」
   - 改后：「start from what **Currently set by** names, and change that: a class, replace it; a rule, change it only when every element it styles is in the scope, and when it styles elements outside the scope too, leave it as it is and override it for this layer only (with Tailwind, a class on the layer; with CSS files or CSS Modules, a rule for the layer's own class).」
   - 后面那句继承文字样式的没动。
2. 「A rule in no CSS layer」：不再给三种写法，覆盖它的类就用 important 形式，是默认写法。
   - 改前：「it beats every class in a CSS layer, whatever their specificity: Tailwind v4 puts its utilities in a layer, so a utility class added over it does not show. Change that rule, narrow it, or, as a last resort, use the class's important form (`bg-blue-600!`).」
   - 改后：「it beats every class in a CSS layer, whatever their specificity. Tailwind v4 puts its utilities in one, so a utility class added over the rule does not show: one that overrides it for this layer only takes its important form (`bg-[#2563EB]!`, `rounded-lg!`).」
   - 两条一致：要不要动规则只在第 1 条说；第 2 条只说在 Tailwind v4 上覆盖用的类怎么写。button-over-rule 里 `button` 规则也管对话框的按钮，按第 1 条不动它、在按钮上写类，按第 2 条这个类用 `!`。
   - 「important form」只跟 Tailwind v4 的工具类说（「Tailwind v4 puts its utilities in one, so …: one that …」）。v3 的工具类不在 layer 里，CSS Modules 的规则也不在，这两种按第 1 条写普通类或规则。
3. 「How the page checks」的样式那一项，在「whatever class or rule gives it」后补：「, and on nothing else: an edit that also changes elements outside the scope is wrong, though `done` says it shows」。只说页面只看这个图层、改过头核对也查不出，没有重复 Scope 那一行。
4. Skill 里没有这几句（`skill/SKILL.md` 只有流程和报告格式），没动。spec 里三处中文转述跟着改了（生成说明下「有样式改动」「当前值来自不在 CSS layer 里的规则」「How the page checks」）。
