# 99: 图层上面多了几行时，页面核对仍找得到挪了位置的图层

**What to build:** ticket 88 的真实跑发现，源码里图层上面多了几行（参数或 JSX 拆成多行、外面包一层），页面核对去找「挪了位置的图层」（`movedElementsOf`）时会找错或找不到，把写对的改动核成没显示，或读了旁边元素的样式。读代码看是两处：

- 它按「现在离图层原来的行最近」挑候选。上面多了 k 行时，紧挨在图层上面的元素反而离原来的行更近，就被挑中（`next-server-usage-text`：`Stat.tsx` 的参数拆成多行后，文字核对读成了数值「5,000」「0」）。
- 它只看自己带源码标记（`data-tk-loc`）的元素。第三方组件渲染的元素只带使用处传下来的 `data-tk-usage`，不在候选里，于是找不到（`third-party` Claude run-1：「the layer is not on the page now」），或挑到 Agent 新加的元素（run-2：读了新包的 `<div>`，三次说「no fill」）。

要做到：图层上面多了行、包了一层，或它是第三方组件的元素时，`done` 仍核到这个图层本身；找不准时如实说找不到，不读别的元素。

参考本功能的 spec.md（同目录上一级），用词以 GLOSSARY.md 为准，并遵守 docs/adr/ 中的决策。

#### 现在怎么找图层（`packages/03kind/src/client/page-elements.ts`）

- **直接命中**：图层涉及的每个文件（元素自己的文件，加上链上每个使用处的文件），页面上的源码标记要和本轮存下的画布一样，才算直接命中。这里也比各组件的使用处。不一样，说明有编辑挪了标记，就按「跟着走」去找。
- **跟着走**：在每个文件里，把画布上和页面上的标记各按源码顺序排好，按种类配对，尽量配上最多的对。种类有三种：元素的标签；只从使用处拿标记的第三方元素；组件的使用处。只有每一种配得最多的配法都把图层配到同一个标记上，才认它。有一种配法把它配到别处，或让它落单，就说找不到。所以不比距离，也就不会因为近而挑中邻居。
- 只带 `data-tk-usage` 的第三方元素也在候选里。
- 删除那一类：图层的标记挪了、在它可能挪去的位置上又有一个看着像它的元素时，结果是「没核对」，不判成已删。原因说「its markers have moved, and an element that looks like it is on the page: the page cannot tell whether that is the layer」。
- 改组件本身的那一类：组件文件的标记挪了时，跟着找到新位置，再核对每个使用处。以前只核对它从哪个使用处提升上来的那一处。
- `stayedPutOf` 和 `otherUsagesThere` 被这套规则取代，删掉了。

#### 真的分不出时

说找不到，不读旁边的元素：`Not checked on the page: the layer is not on the page now. That is no error: go on.` 单测里覆盖了这几种：

- 图层上面的同类元素删了，图层上移一行；
- 两个同标签元素之间写进一个新的；
- 两个一样的兄弟上面又写了第三个（跨两行）；
- 上面的兄弟删了，图层挪到它原来那一行；
- 删除时在可能的位置上有像它的元素：改报「没核对」（见上）。

#### 审查（effort medium，按设计师 2026-11-05 转达的额度决定）

找出 5 处，修了 4 处，前 3 处会出虚假的 ✓：

1. 删除时找不到的图层被当成已删（ticket 99 引入的）。
2. 只有组件的使用处挪了一行、后面没有元素标记时，读到旁边那个使用处（改前就有）。
3. 改组件本身时，标记挪了只核对一处（改前就有）。
4. 「挪去哪」的缓存没按画布分，没有画布的那次查找会把「没找到」存下来。

第 5 处没改：捷径「图层之前的标记一个都没变，就当它没挪」。图层上面写了一个同类元素、从那里到图层的同类元素都往下挪了一位时，会读到新写的那个。改前的代码也读它，所以不是新的虚假的 ✓。去掉这条捷径，会让「在图层后面新加兄弟」这种常见的一轮变成没核对，所以留着，注释里写明了它在哪种情况下错。

审查后加了 8 条单测。审查找出的 5 条虚假 ✓ 和缓存的测试，在修之前的代码上全红。

### 代定的事（待设计师确认）

1. 分不出时一律说找不到，包括「上面的同类兄弟删了，图层上移」：旧代码这时挑剩下那个，碰巧是对的。这种情况的核对覆盖率会比以前低，但不会出虚假的 ✓。
2. 删掉的图层标记挪了、可能的位置上有像它的元素：报「没核对」，不判 ✓。受影响的正确情况有一种：几个一样的、没有文字的元素挨着，删掉其中一个。改前报「没显示」，ticket 99 修第一版时碰巧是 ✓。
3. 没有画布的一轮（产品里不会有，只有测试里有）：标记挪了就找不到，不再按距离猜。改组件本身的改动也一样，不跟着找。
4. 「之前的标记一个都没变，就当没挪」的捷径留着（审查第 5 条），它在哪种情况下错写在注释里。
5. 没改 ADR、GLOSSARY：现有条文都没写到怎么找图层，仍然成立。要不要在 ADR 0006 的 Consequences 里补一句「标记挪了时按本轮画布跟着找，认不出就说找不到」，请设计师定。

### 遗留风险

- 两次编辑落进同一次热更新时，usage 链可能读到旧的使用处（复现第三方时看到的）。这是 `usage-chain.ts` 的问题，这次没动。
- 画布上有、但图层位置上没有元素渲染的使用处（比如元素只在部分使用处显示）：每次都会走「跟着走」，一轮解析一次画布。结果一样，只是慢一些。
- 页面上有、画布上没有的标记（比如冻结后状态变了）：每次核对都走「跟着走」，也只是慢。
- 配对数上限是每个文件 2500 万对，超过就当找不到。真实文件远小于这个数。
- perf 只在无头里比过，有窗口的 perf 和别的线一起在发布前补。
