# 64: 页面自己核对，进度按页面算

**What to build:** 认领之后，代码一变，页面就核对还没显示的改动，进度环按页面上真的显示了几条来长，不再等 Agent 一条条报。`done` 可以一次报多条（如 `done 1 2 3`），每条照样给出核对结果；页面已经核对过的直接返回结果，不用再等。页面看不出来的改动（新建、换容器、改文字、生成说明等）仍按 `done` 算。Skill 里「每条改完立刻 `done`」放宽为「改完一条或一组相关改动后 `done`，`finish` 前至少一次」。`finish` 和手动结束一轮时记下的结果以页面核对为准。

参考本功能的 spec.md（同目录上一级），目标与指标以 docs/goals.md 为准，用词以 GLOSSARY.md 为准，并遵守 docs/adr/ 中的决策（ADR 0013；它修改了 ADR 0005、0006）。

**Blocked by:** 63

**Status:** ready-for-agent

- [ ] 「跳过 `done`」剧本：页面能核对的改动，核对覆盖率 100%
- [ ] 「跳过 `done`」「全改完才一起 `done`」两个剧本：一轮结束时，进度环显示的条数与页面实际显示的条数之差为 0
- [ ] `done 1 2 3` 一次报多条，每条输出核对结果；没显示的给出页面上的实际值和该去查什么，与现在单条时一样
- [ ] 认领期间，约 5000 个元素的大页面上每次热更新的核对不出现 long task（用 22 的性能测试；22 还没合进 main 时，先用 headless trace 量）
- [ ] 真实 Agent（与 63 同一 Agent、同一模型）：每条平均工具调用次数、整轮用时与 63 的基线对比，不高于基线；1:1 落地率、虚假的 ✓ 不变差；前后数字记在 Comments
- [ ] 开发服务器慢时，核对不误报「没显示」：要等这次代码变化的新样式真的到了每个视图（包括手机宽度的视图）再下结论，不只等固定的 3 秒
- [ ] 落地流程里两条在机器忙时会偶尔失败的 e2e 要跑稳，在机器忙时（例如和单测同时跑）各自连续 20 次通过：
  - 「手机视图里做的改动按手机宽度核对」
  - 「认领时还没保存的编辑不进这一轮」：测试要赶在约 0.5 秒的自动保存之前认领，机器一忙就赶不上，属于测试的时序问题
- [ ] Skill、spec 和 GLOSSARY 的「核对」条目随之更新
- [ ] 桌面视图的改动要在每个视图宽度上都核对（包括手机宽度和每个断点视图；某个断点自己单独改过的除外，依据 GLOSSARY「桌面视图中的改动作用于所有断点」和 ADR 0008）。10/31 总调度据 63 的发现加入：63 里两家 Agent 在 Grid 列数场景都只改了 `sm:grid-cols-*`，手机宽度仍是 1 列，核对只看桌面宽度，当成「显示了」放过了。与上面「要等新样式到了每个视图（包括手机宽度）再下结论」一起做。
- [ ] 位置核对按渲染后的实际位置。10/31 总调度据 63 的发现加入：63 里 Cursor 在 absolute 图层上留了 `mt-*`，页面实际位置偏了，可是核对 Y 只读 `top`，误报成「显示了」。

## 背景

- ADR 0006 让 Agent 每条改完立刻 `done`，好在改动还在上下文里时就知道有没有被别的样式盖住。代价是每条多一次工具调用，而且 Agent 不照做时，进度环停住、改动没有核对。
- 页面在代码变化时就核对，Agent 什么时候问都能拿到当时的结果，所以可以放开批量报。
- 编辑层线合并时（2026-10-30）报告：手机宽度的核对最多只等 3 秒，开发服务器 3 秒内没送来新 CSS，就会读到旧值，报「没显示」。e2e 里那条测试因此偶尔失败。误报会让 Agent 去查一个不存在的问题。用户决定在本 ticket 里一并处理。
- 编辑层线修测试素材时（2026-10-30）又发现「认领时还没保存的编辑不进这一轮」那条 e2e 在机器忙时会偶尔失败。它和上一条在同一处测试、同属落地流程，用户（2026-10-31）决定一起交给本 ticket 跑稳。
